Senzu Data API — tài liệu cho team UI

Mọi dữ liệu dashboard (tin nhắn, hội thoại, khách hàng, sản phẩm, trạng thái bot) đều lấy qua một endpoint duy nhất POST /rpc. Mỗi request chỉ định tên hàm và danh sách tham số. Phải có Bearer token và chỉ được gọi từ phía server.

Cập nhật: 06/10/2026 · Nguồn: dashboard/server/data-api.ts, dashboard/lib/queries.ts, dashboard/lib/data-functions.ts

1. Tổng quan

Bot ghi dữ liệu vào SQLite analytics.db trên server Windows tại Việt Nam. Data API chạy cùng máy với bot, đọc DB đó và trả JSON. UI chỉ cần gọi HTTPS, không cần đụng tới database.

2.1. Lớp 1: người dùng đăng nhập vào UI (team UI tự làm)

Data API không biết người dùng cuối là ai, chỉ kiểm tra token. Vì vậy UI mới phải tự chặn người ngoài trước khi hiển thị dữ liệu. Nên làm giống dashboard hiện tại:

  • Dùng Auth.js (next-auth v5) với provider Google. Chỉ cho đăng nhập email @senzu.co.jp có email_verified = true, và từ chối ngay ở callback signIn (không tạo phiên cho email khác).
  • Chặn mọi trang khi chưa đăng nhập (proxy/middleware). Ngoài ra, mỗi server action, route API hay trang nào gọi Data API cũng phải tự kiểm tra lại await auth().
  • Tạo OAuth Client riêng trên Google Cloud Console, với redirect URI là domain của UI mới (ví dụ https://<domain>/api/auth/callback/google). Google không chấp nhận redirect về địa chỉ IP trần.
  • Không dùng Next.js cũng được, miễn là có cơ chế đăng nhập chỉ cho người nội bộ Senzu vào.
// auth.ts — mẫu Auth.js v5 giới hạn domain công ty
import NextAuth from "next-auth";
import Google from "next-auth/providers/google";

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [Google({ clientId: process.env.GOOGLE_CLIENT_ID, clientSecret: process.env.GOOGLE_CLIENT_SECRET })],
  callbacks: {
    async signIn({ profile }) {
      const email = profile?.email;
      return typeof email === "string" && profile?.email_verified === true
        && email.toLowerCase().endsWith("@senzu.co.jp");
    },
  },
});

2.2. Lớp 2: backend UI gọi Data API bằng token

Mọi request tới /rpc phải có header:

Authorization: Bearer <DATA_API_TOKEN>
  • Token dài ít nhất 32 ký tự, được so sánh theo thời gian hằng (timing-safe). Sai hoặc thiếu token sẽ nhận 401 {"error":"unauthorized"}, và server ghi log IP nguồn.
  • Token chỉ nằm ở biến môi trường phía server của UI. Không bao giờ đưa token vào bundle phía client: không dùng tiền tố NEXT_PUBLIC_ và không truyền qua props xuống client component. Trình duyệt chỉ gọi backend UI bằng cookie phiên, backend UI mới là nơi gọi tiếp sang Data API.
Token KHÔNG tự tạo đượcData API so token gửi lên với token đã cài trên server. Token tự nghĩ ra sẽ không khớp và luôn bị 401. Token chỉ có hiệu lực sau khi phía Senzu (người quản trị server chatbot) cài nó vào server.

Quy trình nhận token, chọn một trong hai cách:

  1. Senzu cấp: người quản trị server sinh token, cài vào server, rồi gửi cho team UI.
  2. Team UI tự sinh và gửi Senzu cài: chạy openssl rand -hex 32 (chuỗi ngẫu nhiên, tối thiểu 32 ký tự), gửi cho người quản trị server. Chỉ dùng được sau khi Senzu xác nhận đã cài xong.

Với cả hai cách, token phải được gửi qua kênh bảo mật (trình quản lý mật khẩu, link tự huỷ). Không dán vào Slack, email, ticket hay commit vào repo. Nếu nghi token bị lộ, báo ngay cho Senzu để thu hồi và cấp token mới.

Vì sao phải giữ kín tokenCó token là đọc được toàn bộ tên khách và nội dung tin nhắn Messenger của khách hàng. Ngoài ra token còn ghi được ghi chú khách hàng.

3. Giao thức

Request

POST /rpc
Content-Type: application/json
Authorization: Bearer <token>

{ "fn": "getPeriodStats", "args": [1759683600000, 1759770000000] }
  • fn: tên hàm, phải nằm trong whitelist ở mục 5.
  • args: mảng tham số theo đúng thứ tự của chữ ký hàm, bắt buộc là mảng (hàm không có tham số thì gửi []).
  • Tham số tuỳ chọn có thể bỏ khỏi cuối mảng, hoặc gửi null. Server tự đổi null thành undefined.
  • Body tối đa 64 KB.

Response

200 OK
{ "result": { "incomingCount": 42, "outgoingCount": 40, "distinctCustomers": 9, "avgLatencyMs": 8123, "repliedRatio": 0.95 } }

Dữ liệu luôn nằm trong result. Hàm không trả gì (như insertCustomerNote) có result là null.

Mã lỗi

HTTPBodyNguyên nhân
400{"error":"body không hợp lệ: …"}JSON hỏng hoặc body quá 64 KB
400{"error":"args phải là mảng"}args thiếu hoặc không phải mảng
401{"error":"unauthorized"}Thiếu hoặc sai token
404{"error":"hàm không tồn tại"}fn không thuộc whitelist
404{"error":"not found"}Sai method hoặc path (chỉ có POST /rpc và GET /health)
500{"error":"lỗi truy vấn"}Lỗi khi chạy truy vấn, chi tiết chỉ ghi trong log server
502/504(từ Caddy)Data API trên server đang dừng hoặc khởi động lại
Không có kiểm tra kiểu tham sốServer chỉ kiểm tra tên hàm và việc args là mảng. Gửi sai kiểu (ví dụ chuỗi thay cho số ms) sẽ ra kết quả rỗng/sai hoặc lỗi 500. Hãy validate tham số ở phía UI.

4. Quy ước dữ liệu

Quy ướcChi tiết
Mốc thời gianField có hậu tố Ms, cùng các tham số sinceMs/untilMs, đều là Unix epoch tính bằng mili-giây (UTC).
Bucket ngày/giờbucket và date là chuỗi theo giờ Việt Nam (UTC+7): "YYYY-MM-DD" hoặc "YYYY-MM-DD HH:00".
Khoảng thời giansinceMs tính bao gồm. untilMs tính không bao gồm ([since, until)). Riêng getVolume và getCustomersPerBucket tính untilMs bao gồm (<=).
Tỉ lệrepliedRatio và unresolvedRate nằm trong khoảng 0–1, nhân 100 khi hiển thị %. Là null khi chưa đủ dữ liệu, đừng hiển thị null thành 0%.
Thiếu dữ liệuCác hàm đọc bảng phụ (attention, product_mentions, message_processing, notes) trả mảng rỗng hoặc số 0 nếu bảng chưa có, không trả lỗi.
IDcustomerId = senderId (ID Facebook của khách). conversationId = threadId. Cả hai đều là chuỗi, không phải số.
Độ trễ phản hồiLà ước lượng: ghép tin khách với tin gửi đi kế tiếp trong cùng thread (bỏ cặp nào cách nhau quá 6 giờ). Không phân biệt bot hay nhân viên trả lời.
timestampMs và frameTsMstimestampMs do Facebook gán, lệch khoảng 65 giây so với giờ thật. frameTsMs là giờ bot thực nhận. Dùng timestampMs để sắp xếp và hiển thị.

8. Ví dụ gọi API

curl

curl -X POST https://api-bot.senzu-base.vn/rpc \
  -H "Authorization: Bearer $DATA_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"fn":"getConversations","args":[{"status":"attention","limit":20}]}'

Client TypeScript dùng phía server

// lib/senzu-api.ts — CHỈ import ở server (route handler, server action, server component)
import "server-only";

export class DataApiError extends Error {
  constructor(public status: number, public fn: string, body: string) {
    super(`Data API ${fn} lỗi HTTP ${status}: ${body.slice(0, 300)}`);
  }
}

export async function rpc<T>(fn: string, ...args: unknown[]): Promise<T> {
  const res = await fetch(`${process.env.DATA_API_URL}/rpc`, {
    method: "POST",
    headers: {
      "content-type": "application/json",
      authorization: `Bearer ${process.env.DATA_API_TOKEN}`,
    },
    body: JSON.stringify({ fn, args }),
    cache: "no-store",
    signal: AbortSignal.timeout(15_000), // server ở VN, đi qua internet
  });
  if (!res.ok) throw new DataApiError(res.status, fn, await res.text());
  return ((await res.json()) as { result: T }).result;
}

// Ví dụ: KPI 7 ngày gần nhất so với 7 ngày trước đó
const DAY = 86_400_000;
const now = Date.now();
const [current, previous] = await Promise.all([
  rpc<PeriodStats>("getPeriodStats", now - 7 * DAY, now),
  rpc<PeriodStats>("getPeriodStats", now - 14 * DAY, now - 7 * DAY),

// Ví dụ: chi tiết 1 khách

9. Lưu ý cho team UI

  • Đăng nhập: Data API không biết người dùng cuối là ai, chỉ kiểm tra token. UI mới phải tự làm đăng nhập trước khi cho xem dữ liệu (xem mục 2.1).
  • insertCustomerNote tin tưởng tác giả do bên gọi gửi lên. Luôn lấy authorEmail/authorName từ session. Ghi chú là append-only: không có API sửa hay xoá.
  • Luôn truyền limit hợp lý (20–200). Server không tự giới hạn. Các hàm danh sách hội thoại và khách hàng quét theo từng thread, nên limit lớn sẽ chậm.
  • Gộp request song song bằng Promise.all như ví dụ. Mỗi lời gọi là một round-trip từ hosting của UI sang server ở Việt Nam.
  • Không cache dữ liệu lâu. Bot ghi liên tục. Với số liệu tổng hợp có thể cache ngắn (30–60 giây) ở phía server UI. Với hội thoại và trạng thái bot thì không nên cache.
  • Trạng thái bot: dùng getSystemStatus().isStale để quyết định hiển thị “bot đang chạy” hay không, đừng chỉ dựa vào chromeRunning/messengerConnected.
  • Thêm hàm mới phải làm ở backend: thêm truy vấn vào lib/queries.ts, khai báo trong whitelist lib/data-functions.ts, build lại dist/data-api.mjs và deploy lên server. Hãy gửi yêu cầu cho team backend kèm mô tả dữ liệu cần.
  • Dữ liệu cá nhân: tên khách và nội dung tin nhắn là dữ liệu khách hàng thật. Không đưa vào log phía client, analytics bên thứ ba hay ảnh chụp demo công khai. Khi cần dữ liệu mẫu, hãy dùng dữ liệu giả.
